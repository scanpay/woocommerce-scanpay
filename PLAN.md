# Plan — finishing the v3.0.0 rewrite (`dev` branch)

The `dev` branch is a large rewrite of the plugin (`v3.0.0`, up from `2.9.x`),
roughly 90% done. This file is the authoritative list of the remaining gaps and
how to close them. Work through it top to bottom.

## Working rules

- **Work directly on the `dev` branch, in place.** Edit the files in the main
  checkout — no worktree, no separate branch.
- **Edit only `src/`.** `build/` is a generated release artifact (gitignored) and
  must never be hand-edited — it is regenerated by `./build.sh`.
- **Reset your context between steps.** Each step is self-contained; compact or
  clear after finishing one so stale detail from the previous step doesn't bleed
  into the next.
- **Respect the house conventions** (see `CLAUDE.md`): PHP 8.0 minimum,
  `declare(strict_types=1)`, `defined( 'ABSPATH' ) || exit();` guard, function
  prefix `wc_scanpay_` / `wcs_scanpay_`, text domain `scanpay-for-woocommerce`,
  and **money is always a decimal string** via `src/library/math.php` — never a
  float.
- **Lint before you consider a step done:** `pnpm phpcs` (autofix with
  `pnpm phpcbf`) for PHP; `pnpm lint:js` / `pnpm lint:style` for the frontend.
  Note `lint:js` currently only globs `src/public/assets/js/`, so admin TS
  (`order.ts`, `settings.ts`, and the new `subs.ts`) is **not** covered — check
  those by hand / via `tsc`.
- **Verify the frontend actually builds.** The real build is esbuild inside
  `./build.sh` (over `src/admin/assets/js/*.ts` and `src/public/assets/js/*.ts`),
  not webpack. A `.ts` file only ships once `build.sh` emits its `.js`.
- **One commit per task — on `dev`, kept local.** When a task is finished (lint
  passing and, for frontend work, `build.sh` verified), commit *only that task's*
  changes directly on the `dev` branch as a single, focused commit — e.g.
  `scanpay: reimplement subscription meta-box JS (task 1)`. One task per commit;
  never bundle two tasks or split one task across unrelated commits. Don't commit
  `build/` (gitignored). The investigation/review tasks (8–12) each commit their
  output `.md` file — and, for task 8, any implementation — as that task's commit.
- **NEVER PUSH — this is absolute.** Do **not** run `git push` (including
  `--force`), do **not** open a pull request, and do **not** merge — ever, for any
  reason. Every commit stays **local on `dev`**; the remote is never touched. If
  pushing ever seems necessary, stop and ask the user first. Nothing leaves this
  machine.

## Suggested ordering

Steps 3 + 6 are the same area (order meta box) — do them together. Step 3
establishes the JS meta-box pattern (`types/meta.ts` + `util/compat.ts`), which
step 1 then reuses, so do **3 → 1**. Steps 5 and 7 are quick, independent
cleanups you can slot in anywhere. Step 8 (secret-auth investigation) is
independent — do it whenever, but before the reviews so its outcome is in their
scope. Steps 9–12 (reviews + prioritization) come last, after the code is
complete. Commit each task separately (on `dev`, never pushed) as you finish it
(see Working rules).

## 1) Reimplement the Subscription meta-box JS (`subs.ts`)

**Goal:** restore the Scanpay meta box on the WooCommerce Subscription admin
screen. It was removed in the rewrite and never rebuilt, so the box is currently
broken in production.

**Where it stands:**
- `src/admin/subscriptions.php` (line 47) enqueues handle `wcsp-meta` →
  `admin/assets/js/subs.js` with `defer`, but **`src/admin/assets/js/subs.ts`
  does not exist**, so `build.sh` emits no `subs.js` — the enqueue 404s.
- The PHP (`wc_scanpay_create_meta_box_subs`, lines 22–32) renders this shell and
  passes data via `data-*` attributes only (no `wp_localize_script`):
  ```html
  <div id="wcsp-meta" data-secret="…" data-subid="…" data-payid="…" data-ptime="…">
    <div id="wcsp-meta-head"></div>
    <ul id="wcsp-meta-ul" class="wcsp-meta-ul"></ul>
  </div>
  ```
  Note: this box has **no `#wcsp-meta-foot`** (unlike the order box in step 3).
- Backing data comes from the long-poll endpoint
  `src/admin/ajax/wp-scanpay-fetch-sub.php`: authenticate with `data-secret`
  (compared via `hash_equals` to `settings['secret']`), pass `?subid=` + `?rev=`,
  and it returns the `scanpay_subs` row as JSON with 0.5→8s backoff.

**Correction to the old plan / CLAUDE.md:** the `scanpay_subs` table
(`src/install.php` lines 53–59) has only `subid, rev, method, method_exp`. There
are **no `retries`, `idempotency-key`, or `nxt` columns** — that state is not
persisted (the idempotency key is derived statelessly in
`src/library/class-wcs-scanpay-charge.php` as `orderid_rev_day`). So the box can
only surface `rev`, `method`, and `method_exp`; do **not** try to display
retries/idem/nxt. (Flag this schema/CLAUDE.md mismatch when you're done.)

**Do:**
- Create `src/admin/assets/js/subs.ts`. Read `data-secret/-subid/-payid/-ptime`
  off `#wcsp-meta`, long-poll `wp-scanpay-fetch-sub.php`, and render the returned
  card method + expiry (and payment id/time from the data attributes) into
  `#wcsp-meta-ul`.
- Reuse the shared helpers instead of re-inventing them: `buildTable` /
  `showWarning` / `showError` from `admin/assets/js/types/meta.ts`, and
  `checkVersion` etc. from `admin/assets/js/util/compat.ts`. Land step 3 first so
  those helpers are already exercised by `order.ts`.

**Done when:** `build.sh` emits `admin/assets/js/subs.js`, the box renders the
subscription's card/method info on both HPOS and legacy screens, and no console
errors fire.

## 2) Wire up the settings sync-status UI

**Goal:** show last-sync / out-of-sync / new-version warnings and the "send ping"
flow on the gateway settings page. The JS for this ships but the PHP never emits
the elements it needs, so none of it runs.

**Where it stands — `src/admin/assets/js/settings.ts` targets (and
`src/admin/settings/admin-options.php` renders none of):**
- `#wcsp-set-alert` with `data-secret` and `data-shopid` — the anchor the script
  reads config from (`settings.ts` lines 64–65, 24).
- `#wcsp-set-nav-mtime` — where the "Synchronized: N seconds ago" string is
  written (line 39). **This is non-null asserted (`!`)** — if the element is
  absent the script throws, which is part of why the page is currently silent.
- `#woocommerce_scanpay_apikey` — WC-generated field, used only when `shopid===0`
  to inject a "find your API key here" hint.

**Behavior the script implements once the elements exist:**
- `shopid === '0'`: hint pointing to where the API key lives.
- otherwise `checkMtime()` fetches last-sync via `…/wp-scanpay/fetch?x=ping&s=<secret>`
  and branches: `0` → "initiate synchronization / send ping"; `<400s` → writes
  the "synchronized N s ago" string into `#wcsp-set-nav-mtime`; `<604800s` →
  "may be out of sync"; else "out of sync". Re-runs on `visibilitychange`.
- `checkVersion()` compares the GitHub latest release to the `{{ VERSION }}` build
  placeholder and shows a "new version available" warning.

**Do:** in `admin-options.php`, render the `#wcsp-set-alert` box (with
`data-secret` = `settings['secret']` and `data-shopid` = the shop id parsed from
the API key) and the `#wcsp-set-nav-mtime` element in the nav bar. Match the DOM
shape `settings.ts` already assumes so no selector rewiring is needed.

**Done when:** a synced shop shows "Synchronized N seconds ago", a stale/never-
synced shop shows the appropriate warning + ping affordance, an out-of-date
plugin shows the version warning, and the settings page throws no JS errors.

**Done when:** the box shows the transaction figures, surfaces warnings inline

## 8) Investigate a better alternative to the admin-AJAX shared secret

**Goal:** decide whether `settings['secret']` — the shared secret that
authenticates the lightweight admin polling endpoints — should be replaced with
something stronger, and implement the replacement if a clearly better option
exists. Record the decision either way (including "keep as-is").

**Where it stands (how it works today):**
- The secret is minted once in `src/install.php` (`bin2hex( random_bytes( 32 ) )`,
  256-bit) and stored inside the **autoloaded** `woocommerce_scanpay_settings`
  option under `['secret']` (no separate option).
- It is rendered into admin pages as a `data-secret` attribute (`#wcsp-set-alert`
  on the settings page; `#wcsp-meta` on the order and subscription meta boxes).
- The polling JS (`settings.ts`, `order.ts`, the future `subs.ts`) reads
  `data-secret` and calls `…/wp-scanpay/fetch?x=meta|ping|sub&s=<secret>` with an
  `X-Scanpay` request header.
- `src/woocommerce-scanpay.php` (lines 83–95) short-circuits on
  `isset( $_SERVER['HTTP_X_SCANPAY'], $_GET['x'], $_GET['s'] )`, `match`es `?x=`
  to one of `admin/ajax/wp-scanpay-fetch-{meta,ping,sub}.php`, `require`s it, and
  `return`s — **before** the plugin registers gateways/hooks and before WooCommerce
  boots.
- Each endpoint authenticates with only `get_option()` +
  `hash_equals( $secret, rtrim( $_GET['s'] ) )`, then does its DB work (long-poll
  on `scanpay_seq` / `scanpay_subs`; read `scanpay_meta`). **All three are
  read-only.**

**Why the secret exists (verify this premise first):** the belief is it was a
performance trick to avoid booting all of WooCommerce on these frequently-hit,
long-held polling requests. The deeper reason: the short-circuit runs during the
plugin-include phase, **before WP's pluggable functions and the current-user /
auth-cookie machinery load**, so a normal WP nonce (`wp_verify_nonce` /
`check_ajax_referer`) isn't even available yet and there is no established user
session — the secret is verifiable with just an option read. **Confirm the
premise with data:** measure wall-clock + peak memory of the current fast path
vs. a full `admin-ajax.php`/REST request that boots WC, on a realistic install
(WC + WooCommerce Subscriptions active). This is a data-driven decision — if the
saving is negligible, the trick may not be worth its security cost.

**Weaknesses to weigh:**
- The secret rides in the **query string** (`?s=`), so it leaks into web-server
  access logs, proxy logs, browser history, and `Referer` headers — the biggest
  concrete weakness.
- It is a single **shop-wide, non-expiring** token shared by every admin; it never
  rotates and lives in an autoloaded option.
- Read-only endpoints cap the blast radius of a leak at information disclosure
  (sync status, order-meta totals, a subscription's card label/expiry) — no state
  mutation — but that is still unauthenticated data exposure if the token leaks.

**Alternatives to evaluate (with the perf numbers in hand):**
1. **Minimal hardening — move the secret out of the URL** into the existing
   `X-Scanpay` header (or an `Authorization: Bearer` header). Keeps the exact fast
   path and auth model; removes the access-log/`Referer` leak. Lowest risk/effort
   and a sensible fallback if nothing heavier is justified.
2. **Short-lived HMAC token** embedded in the page instead of the raw secret:
   `token = expiry . ':' . hash_hmac( 'sha256', user_id . '|' . expiry, secret )`;
   the endpoint verifies with `hash_hmac` + `hash_equals` + an expiry check —
   still just an option read, no user session, no WC. Adds expiry and optional
   per-user binding while preserving the WC-free path. Combine with (1) for
   transport.
3. **Real WP nonce via `admin-ajax.php` or the REST API** (`check_ajax_referer` /
   `permission_callback` + `current_user_can`). Idiomatic, per-user, expiring —
   but requires letting WP (and typically WC) bootstrap fully and holding a
   long-poll open on a fully-booted worker. Choose only if the measurement shows
   the bootstrap cost is acceptable; otherwise document why it was rejected.
4. **Rotating / per-user server-minted token** (a transient keyed to the user, or
   WP application passwords) — likely overkill for read-only polling; evaluate
   briefly and probably reject.

**Do:** run the measurement, write the comparison + recommendation to
`secret-auth-review.md`, then implement the chosen option (expected: at least
alternative 1, possibly 2). Keep the endpoints WC-free unless the measurement
proves that's unnecessary. If the conclusion is "keep the secret as-is", state
that explicitly with the data that justifies it.

**Done when:** `secret-auth-review.md` records the perf measurement, the options
weighed, and the decision; any chosen change is implemented, lints clean, and all
three polling flows still authenticate end-to-end (settings sync, order meta,
subscription meta). Commit the write-up and any implementation as this task's
commit (local only — never pushed).
