# Scanpay for WooCommerce — agent guide

WordPress/WooCommerce payment gateway for [Scanpay](https://scanpay.dk): card,
MobilePay Online and Apple Pay, plus WooCommerce Subscriptions. HPOS- and
Blocks-compatible.

This is the one guide, and it is deliberately high-level and slow-moving: what a file
does belongs in that file's comments, not here. Per-tool entry points such as
`.claude/CLAUDE.md` are symlinks — edit this file, never add a second copy.

## Build and validation

- `src/` is the authored source — **edit here, never `build/`**, a gitignored artifact
  regenerated by `./build.sh` and shipped manually to customers and WordPress.org.
- `./build.sh` is the whole build, no webpack: rsync `src` → `build`, sass, esbuild for
  TS, wp-cli i18n, `{{ VERSION }}`-style substitution from `package.json`, and an
  optional rsync-deploy to the test server. A `.ts` file only ships once esbuild emits
  its `.js`.
- **pnpm, not npm** (`package-lock.json` is gitignored).
- **The linters are the validation.** No test suite runs here, so `pnpm phpcs` (autofix
  `pnpm phpcbf`), `pnpm lint:js`, `pnpm lint:style` and `pnpm exec tsc` — there is no
  `tsc` script, hence `exec` — are what a change is checked against; all four clean
  before calling it done. They see syntax, style and types only. Anything that needs a
  running shop stays **unverified**: say so rather than imply it was tested.
- **Never raise a version floor to reach a newer API** — anything above the floor needs
  a runtime guard. `pnpm phpcs` enforces the PHP floor (PHPCompatibilityWP); the WP and
  WC floors are yours to check, and `vendor/php-stubs/` carries the `@since` tags, so
  read the stub instead of trusting memory. `docs/requirements.md` has the rationale for
  each minimum. The full WP/WC/WCS trees are symlinked into `.stubs/` when a claim turns
  on a method body the stub does not carry — cite that path, not the target it resolves to.

## Code style: procedural and modular, not OOP

**A deliberate preference, not legacy code.** Do not "modernize" it into classes. It is
what keeps the plugin cheap to load on every request to the whole site, auditable end to
end from HTTP request to `curl_exec`, and a natural fit for a procedural, hook-based host.

- **The file is the module.** The `require` list in `woocommerce-scanpay.php` is the
  linker; the `wc_scanpay_` / `wcs_scanpay_` prefixes are the namespace. There is no
  autoloader and the shipped plugin has **zero runtime dependencies** — do not add
  either. (`composer.json` is `require-dev` only; nothing from `vendor/` ships.)
- **Data stays in primitives.** Money is a decimal string, DB rows are `ARRAY_A`,
  settings are arrays. No value objects, no DTOs — validate at the boundary.
- **A class only earns its place when it holds a resource or state across calls**, or
  when WooCommerce's contract demands one (the gateways, the Blocks support class).
  Everything else is a free function. Concrete classes are `final`; the only inheritance
  is the one WC requires. No interfaces, traits or DI containers — do not introduce any.
- **`require` doubles as a call.** A settings-field file returns an array;
  `admin-options.php` is a template taking a `$gateway` handle. Intentional — do not
  refactor it away. The bound is that a required file never relies on inherited class
  scope: bare `$this`, `parent::` or a protected call means it is a method body in the
  wrong file, and belongs in the gateway (where WC's contract already earns a class).
- **Fail loud.** Primitives throw; one place per flow catches. A typed parameter is the
  preferred guard — a `TypeError` beats a defensive `if`.

The accepted cost is that nothing here is unit-testable (behaviour is verified on a real
shop) and no tool checks array field names. Comments are the compensation, and what
verification runs on: a change is checked against the invariants they state, so a comment
that has drifted is a broken test.

## Comments

**Write** the constraint, the protocol quirk, the reason behind a deliberate omission,
the failure the line prevents — whatever a reviewer would ask "why is this here?" about.
**Never write** a restatement of the next line, a change log, or a `@param`/`@return`
block repeating types the signature already states. **Keep them short.** Dense means
precise, not long: one exact sentence beats two, and two beat a paragraph.

- **File header — required, except in `woocommerce-scanpay.php` and files whose purpose
  is self-evident:** `/** … */` between `<?php` and `declare`. A sentence or two on what
  the file is for, plus a `Contract:` list when it speaks a wire protocol (method, body
  shape, headers).
- **Function docblock:** `/** … */` prose. Add `@return array{…}` when the shape is not
  obvious, `@throws` for what a caller must catch, `@internal` outside the module's
  surface.
- **Inline `//`:** own line above the code, or trailing for a short aside. Full
  sentences, English, ending in a period.
- **`phpcs:ignore`** always carries `-- <reason>`.
- PHPCS enforces docblock *shape* and commented-out code, nothing more — no
  `@param`/`@return` ceremony to satisfy, but a multi-line docblock needs a short
  description line and prose must not look like code.

## Conventions

- Every PHP file opens with `declare(strict_types=1);` and
  `defined( 'ABSPATH' ) || exit();`.
- **Money is never a float.** Decimal strings through `src/library/math.php` for all
  capture, charge and refund arithmetic.
- Text domain `scanpay-for-woocommerce`, English source strings. `./build.sh` owns
  extraction: it re-derives `src/languages/*.pot|*.po` from the built tree on every run,
  deterministically, and emits the MO/PHP/JSON catalogs into `build/`. There is no
  separate `pnpm` i18n script. Settings-field *defaults* stay plain strings — `__()`
  cannot localize a stored value.
- Production hosts are `*.scanpay.dk`; `build.sh` rewrites them to `*.scanpay.dev` in the
  test build only.
- **Commit subjects carry no `scanpay:` prefix** — every commit here is a Scanpay change,
  so write the summary directly. Older commits still carry it; do not rewrite them and do
  not copy the style.

## Architecture

`src/woocommerce-scanpay.php` is the router. Before registering anything it dispatches
three request types that must skip the rest of the bootstrap: the HMAC-signed ping, the
payment-return page, and the admin AJAX endpoints (authenticated by a shared secret that
lives inside the settings option). Each gate states its own reasoning in place.

Otherwise it registers three gateways — card, MobilePay, Apple Pay — all extending
`WC_Gateway_Scanpay_Base`. **Only the card gateway supports subscriptions.** Card
settings are the primary/shared option holding the API key; the other two use the usual
`woocommerce_{id}_settings`.

**Payment flow:** checkout → payment link → the Scanpay payment window → Scanpay pings
back → HMAC-verified drain → `WC_Scanpay_Sync` upserts `scanpay_meta` and calls
`payment_complete()`. Capture runs on order completion. Renewals go to
`WCS_Scanpay_Charge`. Refunds are dashboard-only: `can_refund_order()` is false and sync
reflects them read-only. `WC_Scanpay_Client` (curl) is the only code that talks to the
API.

**Ping/sync** ([docs](https://docs.scanpay.dev/synchronization)) is the backbone: Scanpay
posts its sequence number, the plugin compares it against the local cursor and drains the
changes under `Scanpay_Flock`. Replaying a drain is always safe: it rebuilds every meta
row without re-firing `payment_complete()`, which is what makes wiping the local tables a
recoverable act. Tables (latin1): `scanpay_seq`, `scanpay_meta`, `scanpay_subs`.

**The subscription terms checkbox is cart-level consent, not a payment-method feature** —
do not re-scope it to the card gateway. One predicate drives both rendering and
validation, in classic checkout and in Blocks, for whichever gateway the customer picks:
ours or a third party's, enabled or not.

**Frontend TS**, bundled by esbuild: `public/assets/js/` is checkout, including the Blocks
registration; `admin/assets/js/` is the admin screens and their shared runtime helpers.

## Settled — do not "fix" these

Cross-cutting decisions that no single file owns. Everything else that looks odd is
answered by a comment at the line itself; read it before flagging.

- **Scanpay pings every 5 minutes regardless of changes.** That keepalive is the recovery
  backstop for the whole design — a dropped or stranded ping self-heals within minutes,
  so never add retry or recovery machinery justified by "otherwise it is lost forever".
- **Charge concurrency is lock-free.** No DB lock, no `nxt` timestamp, no key rotation.
  The layers are local already-paid guards, a stateless `Idempotency-Key` that Scanpay
  enforces server-side at ≤1 charge per key per 24 h, and WCS owning retry scheduling.
- **The admin-AJAX secret is unscoped, and stays that way.** No capability, no per-order
  token, no rate limit: the endpoints dispatch before `pluggable.php` is included, and
  order-editing access on a WooCommerce shop is all-or-nothing, so scoping would gate
  nothing the holder cannot already read. A role granting *partial* order access would be
  new information; nothing else is.
- **The API key is write-once.** Masked once set, never rendered back, and an empty POST
  means *unchanged*. Replacing a stored key is refused; the reset button is the only way,
  and short of uninstalling, the only thing that deletes data.
- **Migrations stamp the version last**, so an interrupted run retries from the start, and
  they discriminate on the settings option rather than the version — 1.x wrote settings
  but never a version. One file per version in `src/upgrade/`, run from the ordered list in
  `upgrade.php`: the list is the gate, never a scan of the directory. There is no activation
  hook — that same gate is the install path.
