# Scanpay for WooCommerce — agent guide

> One guide for every coding agent. `CLAUDE.md` is a symlink to this file — edit
> here; there is no second copy.

WordPress/WooCommerce payment gateway for [Scanpay](https://scanpay.dk): card,
MobilePay Online and Apple Pay, plus WooCommerce Subscriptions. HPOS- and
Blocks-compatible.

## Layout, build, lint

- `src/` is the authored source — **edit here, never `build/`**, a gitignored
  artifact regenerated by `./build.sh` and shipped manually to customers and
  WordPress.org.
- `docs/requirements.md` holds the rationale for every WP/WC/PHP minimum. Read it
  before reaching for a newer API: anything above the floor needs a runtime guard,
  not a version bump.
- **pnpm, not npm** (`package-lock.json` is gitignored).
- `./build.sh` is the whole build, no webpack: rsync `src` → `build`, sass, esbuild
  for TS, wp-cli i18n, `{{ VERSION }}`-style substitution from `package.json`, and
  an optional rsync-deploy to the test server (ssh alias `modules`). A `.ts` file
  only ships once esbuild emits its `.js`.
- Before calling a change done: `pnpm phpcs` (autofix `pnpm phpcbf`),
  `pnpm lint:js`, `pnpm lint:style`, and `tsc` — `lint:js` does not type-check.

## Code style: procedural and modular, not OOP

**A deliberate preference, not legacy code.** Do not "modernize" it into classes.
It is what keeps the plugin cheap to load on every request to the whole site,
auditable end to end from HTTP request to `curl_exec`, and a natural fit for a
procedural, hook-based host.

- **The file is the module.** The `require` list in `woocommerce-scanpay.php` is the
  linker; the `wc_scanpay_` / `wcs_scanpay_` prefixes are the namespace. There is no
  autoloader and the shipped plugin has **zero runtime dependencies** — do not add
  either. (`composer.json` is `require-dev` only; nothing from `vendor/` ships.)
- **Data stays in primitives.** Money is a decimal string, DB rows are `ARRAY_A`,
  settings are arrays. No value objects, no DTOs — validate at the boundary.
- **A class only earns its place when it holds a resource or state across calls**
  (`WC_Scanpay_Client`, `Scanpay_Flock`, `WC_Scanpay_Sync`) or when WooCommerce's
  contract demands one (the gateways, the Blocks support class). Everything else is
  a free function. Concrete classes are `final`; the only inheritance is the one WC
  requires. No interfaces, traits or DI containers — do not introduce any.
- **`require` doubles as a call.** A settings-field file returns an array;
  `process-admin-options.php` runs in the gateway's scope with `$this` live.
  Intentional — do not refactor it away.
- **Fail loud.** Primitives throw; one place per flow catches. A typed parameter is
  the preferred guard — a `TypeError` beats a defensive `if`.

The accepted cost is that nothing here is unit-testable (verification happens on a
real shop) and no tool checks array field names. Comments are the compensation.

## Comments

**Write** the constraint, the protocol quirk, the reason behind a deliberate
omission, the failure the line prevents — whatever a reviewer would ask "why is
this here?" about. **Never write** a restatement of the next line, a change log, or
a `@param`/`@return` block repeating types the signature already states. Dense
means precise, not long: two exact sentences beat a paragraph.

- **File header:** `/** … */` between `<?php` and `declare`. One paragraph on what
  the file is for, plus a `Contract:` list when it speaks a wire protocol (method,
  body shape, headers).
- **Function docblock:** `/** … */` prose. Add `@return array{…}` when the shape is
  not obvious, `@throws` for what a caller must catch, `@internal` outside the
  module's surface.
- **Inline `//`:** own line above the code, or trailing for a short aside. Full
  sentences, English, ending in a period.
- **`phpcs:ignore`** always carries `-- <reason>`.
- PHPCS enforces only docblock *shape* and commented-out code — no
  `@param`/`@return` ceremony to satisfy, but a multi-line docblock needs a short
  description line and prose must not look like code.

## Conventions

- Every PHP file opens with `declare(strict_types=1);` and
  `defined( 'ABSPATH' ) || exit();`.
- **Money is never a float.** Decimal strings through `src/library/math.php`
  (`wc_scanpay_addmoney`, `_submoney`, `_cmpmoney`, `_money_equals`, `_is_zero`,
  `_is_money`) for all capture, charge and refund arithmetic.
- Text domain `scanpay-for-woocommerce`, English source strings, `.pot` via
  `pnpm i18n:po`. Settings-field *defaults* stay plain strings — `__()` cannot
  localize a stored value.
- Production hosts are `*.scanpay.dk` (API, dashboard, and `betal` for the payment
  window); `build.sh` rewrites them to `*.scanpay.dev` in the test build only.
- **Commit subjects carry no `scanpay:` prefix** — every commit here is a Scanpay
  change, so write the summary directly. Older commits still carry it; do not
  rewrite them and do not copy the style.

## Architecture

`src/woocommerce-scanpay.php` is the router. It dispatches three special request
types before registering anything else:

- `X-Signature` header → `callback/wc-scanpay-ping.php` (ping/sync) via the WC API
  endpoint `woocommerce_api_wc_scanpay`; no other plugin hook runs.
- `?scanpay_thankyou` + `?scanpay_type` + `?key` → `public/wp-scanpay-thankyou.php`.
- `X-Scanpay` header (shared secret) + `?x=…` → `admin/ajax/wp-scanpay-fetch-*.php`.
  The secret lives *inside* the settings option, minted by `install.php`.

Otherwise it registers three gateways — card, MobilePay, Apple Pay — all extending
`WC_Gateway_Scanpay_Base`. **Only the card gateway supports subscriptions.** Card
settings are the primary/shared option; the other two use the usual
`woocommerce_{id}_settings`. Form fields lazy-load from
`admin/settings/fields/<id>.php`.

**Payment flow:** checkout → `public/generate-payment-link.php` →
`WC_Scanpay_Client::new_url` → redirect to the payment window. Scanpay pings back →
HMAC-verified drain → `WC_Scanpay_Sync` upserts `scanpay_meta` and calls
`payment_complete()`. Capture runs on order completion, always through
`WC_Scanpay_Capture::capture_or_hold` (the mark-completed AJAX intercept registers
*before* WC's own handler so capture precedes completion emails). Refunds are
dashboard-only — `can_refund_order()` is false and sync reflects them read-only.
Renewals go to `WCS_Scanpay_Charge`. `WC_Scanpay_Client` (curl) is the only code
that talks to the API.

**Ping/sync** ([docs](https://docs.scanpay.dev/synchronization)): POST
`{seq, shopid}`, header `X-Signature: base64(hmac_sha256(body, apikey))`. Compare
the ping against the local cursor `scanpay_seq.seq` — lower → 400 (replay); equal →
heartbeat, touch `mtime` only (the common case, and what drives the "last sync"
indicator); higher → drain under `Scanpay_Flock`. `seq` is only trustworthy while
the flock is held, so re-read it after every acquire. A drain that gets no changes
while still below target **throws** rather than ack a sync that did not happen.
Tables (`install.php`, latin1): `scanpay_seq`, `scanpay_meta`, `scanpay_subs`.

**The subscription terms checkbox is cart-level consent, not a payment-method
feature** — do not re-scope it to the card gateway. One predicate (a subscription in
the cart *and* `wcs_scanpay_terms_url()` resolving a published page) drives both
rendering and validation, in classic checkout and in Blocks, for whichever gateway
the customer picks — ours or a third party's, enabled or not. In Blocks the payload
key therefore sits outside `methods` and outside the `enabled` gate; both paths
share one msgid.

**Frontend TS**, bundled by esbuild: `public/assets/js/checkout.ts` registers the
Blocks methods — Apple Pay only where `ApplePaySession.canMakePayments()` is true.
`admin/assets/js/` holds the admin screens and their shared runtime helpers.

## Lifecycle

- `install.php` runs on every activation and is idempotent. A fresh install stamps
  the version so the loader skips `upgrade.php`. **"Fresh" means an absent settings
  option, not an absent version** — 1.x wrote settings but never a version, so
  gating on the version would skip its migration and silently disable auto-capture.
- `upgrade.php` migrations are version-gated and stamp the version **last**, so an
  interrupted run retries from the start. On failure the loader deliberately keeps
  the `wc_scanpay_updating` transient: one retry per 5 minutes beats fataling
  `plugins_loaded` and taking out wp-admin.
- **The API key is write-once.** Masked once set and never rendered back; an empty
  POST means *unchanged* (WC's password handling would wipe it); replacing a stored
  key is refused, the reset button is the only way. Enabling or first setting a key
  validates it with a live `seq(0)` — a UX check, nothing destructive hangs off it.
- **Only the reset button deletes data**: it drops the tables, clears the key,
  disables the gateways and re-runs `install.php`. Safe because sync replay rebuilds
  every meta row without re-firing `payment_complete()`. `uninstall.php` drops the
  tables, options and transient.

## Settled — do not "fix" these

Each looks like a bug and is not.

- **Charge concurrency is lock-free.** No DB lock, no `nxt` timestamp, no key
  rotation. The layers are local already-paid guards (including an authoritative
  `scanpay_meta` SELECT), a stateless `Idempotency-Key` that Scanpay enforces
  server-side at ≤1 charge per key per 24 h, and WCS owning retry scheduling.
- **Scanpay pings every 5 minutes regardless of changes.** That keepalive is the
  recovery backstop for the whole design — a dropped or stranded ping self-heals
  within minutes, so never add retry or recovery machinery justified by "otherwise
  it is lost forever". On lock contention we record the seq, answer 200 and let the
  incumbent drain it: a latency optimization, not a correctness requirement.
- **The flock file lives in the system temp dir**; `WP_TEMP_DIR` is the escape hatch.
- **`scanpay_subs` stores no retries, idempotency key or `nxt` lock**, and `method`
  there is the payment-method *type*, not the pretty card label.
- **`get_title()` returns `'Scanpay'` under `is_admin()`** — deliberate branding.
  Sync collapses all three gateways into the `scanpay` payment method and owns the
  real `payment_method_title`.
- **`$this->icon` is not dead** despite the `get_icon()` overrides: WooCommerce reads
  the raw property for the admin Payments list.
- **The missing `cart_checkout_blocks` compatibility declaration is a no-op** — the
  feature defaults to compatible and WC's notice lists only explicit *negative*
  declarations (HPOS is the disanalogy).

Verified sound, do not re-audit: ping/sync, `math.php`, the flock, client TLS,
capture money math, secret auth.
