# Scanpay for WooCommerce

> A Codex-facing twin of this file lives at `AGENTS.md`. Keep the two in sync —
> when you change project facts here, mirror them there.

WordPress/WooCommerce payment gateway for [Scanpay](https://scanpay.dk): card,
MobilePay Online, and Apple Pay; WooCommerce Subscriptions; HPOS- and
Blocks-compatible. `dev` is the feature-complete `v3.0.0` rewrite (up from
`2.9.x`).

## Layout

- `src/` — authored source. **Edit here, never `build/`** (gitignored release
  artifact regenerated by `./build.sh`, shipped manually to customers /
  WordPress.org).
- `vendor/` — Composer dev tooling only (phpcs, wp-cli), not shipped.
  `node_modules/` — pnpm deps. `.stubs/` — phpactor symlinks, gitignored.
- `docs/requirements.md` — rationale for every WP/WC/PHP minimum version; check
  it before using a newer API.

## Build & lint

- **pnpm, not npm** (`package-lock.json` is gitignored).
- `./build.sh` is the real build (no webpack): rsync `src` → `build`, `sass`,
  `esbuild --bundle --minify` for TS, wp-cli i18n, then substitutes
  `{{ VERSION }}` / `{{ WP_MIN }}` / etc. from `package.json`. A `.ts` file only
  ships once esbuild emits its `.js`. Optionally rsync-deploys to the test
  server `woocommerce.scanpay-modules.dev` (ssh alias `modules`), rewriting
  `*.scanpay.dk` → `*.scanpay.dev` in that copy only.
- Lint before considering a change done: `pnpm phpcs` (autofix `pnpm phpcbf`;
  WordPress + WooCommerce-Core + PHPCompatibilityWP, short arrays) and
  `pnpm lint:js` / `pnpm lint:style`. `lint:js` covers all `src/` TS but does
  not type-check — run `tsc` (tsconfig is `noEmit`; its `include` globs govern
  coverage).

## Conventions

- PHP 8.0 minimum. Every file: `declare(strict_types=1)` +
  `defined( 'ABSPATH' ) || exit();`. WordPress function-based style, prefixes
  `wc_scanpay_` / `wcs_scanpay_`.
- Text domain `scanpay-for-woocommerce`, English source strings, `.pot` via
  `pnpm i18n:po`. Settings-field *defaults* (checkout title/description) are
  deliberately plain strings — `__()` cannot localize a stored value.
- **Money is never a float.** Decimal strings via `src/library/math.php`:
  `wc_scanpay_addmoney` / `_submoney` / `_cmpmoney` / `_money_equals` /
  `_is_zero` / `_is_money`. Use these for all capture/charge/refund arithmetic.
- Prod hosts: `api.scanpay.dk`, `dashboard.scanpay.dk`, `betal.scanpay.dk`
  (payment window). `.dev` variants exist only in the deployed test build.
- **Commit subjects carry no `scanpay:` prefix.** Every commit in this repo is a
  Scanpay change, so the prefix is noise. Write the summary directly — e.g.
  `leave phone numbers unchanged with no calling code (task 5)`. Commits before
  2026-07-20 still carry it; do not rewrite them, and do not copy the style.

## Architecture

`src/woocommerce-scanpay.php` routes special requests before registering
anything:

- `X-Signature` header → `callback/wc-scanpay-ping.php` (ping/sync) via the WC
  API endpoint `woocommerce_api_wc_scanpay`; the plugin's other hooks are
  skipped.
- `?scanpay_thankyou` + `?scanpay_type=wc|wcs|wcs_free` + `?key` →
  `public/wp-scanpay-thankyou.php`, required immediately.
- `X-Scanpay` header (shared secret) + `?x=meta|ping|sub` →
  `admin/ajax/wp-scanpay-fetch-{meta,ping,sub}.php`, required immediately. The
  secret lives *inside* the settings option (minted by `install.php`), not in a
  separate option.

Otherwise it registers gateways `scanpay` (card), `scanpay_mobilepay`, and
`scanpay_applepay`, all extending `WC_Gateway_Scanpay_Base` (`src/gateways/`).
**Only the card gateway supports subscriptions.** Form fields lazy-load from
`admin/settings/fields/<id>.php`. Settings options:
`woocommerce_scanpay_settings` (card = primary/shared; `WC_SCANPAY_URI_SETTINGS`)
plus the usual `woocommerce_{id}_settings` for the other two.

Subscription terms checkbox (shown when WCS is active and the configured terms
page is still *published*): classic checkout renders
`public/wcs-scanpay-checkout-terms.php` and enforces via
`wcs_scanpay_validate_terms`; Blocks renders it inside the card method's content
(`checkout.ts`) and enforces via `wcs_scanpay_blocks_validate_terms` (only the
card gateway supports subscriptions).

**Payment flow:** checkout → `public/generate-payment-link.php` →
`WC_Scanpay_Client::new_url` → redirect to `betal.scanpay.dk`. Scanpay pings
back → HMAC-verified drain loop pulls changes (`seq`) → `WC_Scanpay_Sync`
upserts `scanpay_meta` and calls `payment_complete()`. Capture runs on order
completion — the status hook, the bulk actions (`admin/orders.php`,
`admin/hooks/wp-bulk-actions.php`), the mark-completed AJAX intercept
(registered *before* WC's own handler so capture precedes completion emails), or
the order meta-box button — via `WC_Scanpay_Capture::capture_or_hold`. Refunds
are dashboard-only (`can_refund_order()` is false); sync reflects them
read-only. Renewals: `woocommerce_scheduled_subscription_payment_scanpay` →
`WCS_Scanpay_Charge`.

`WC_Scanpay_Client` (`src/library/class-wc-scanpay-client.php`, curl) is the
only code that talks to `api.scanpay.dk`.

**Ping/sync** ([docs](https://docs.scanpay.dev/synchronization)): POST
`{seq, shopid}` (capped at 512 bytes), header
`X-Signature: base64(hmac_sha256(body, apikey))`. **Scanpay pings every 5
minutes regardless of changes.** That keepalive is the recovery backstop for the
whole design: a dropped/stranded ping self-heals within ~5 minutes, so never add
ping-retry or recovery machinery justified by "otherwise it's lost forever".
Pings retry until we answer 200 and time out after ~7 s (backend-team knowledge;
not in the docs).

`wc-scanpay-ping.php` vs the local cursor `scanpay_seq.seq`: lower → 400
(replay); equal → heartbeat, update `mtime` only (the common case; drives the
settings "last sync" indicator); higher → drain under `Scanpay_Flock` (per-shop
lock file in the system temp dir — by design; `WP_TEMP_DIR` is the escape hatch)
to target `max( ping_seq, ping )`. `seq` is only trustworthy when read **under
the flock** — re-read it after every acquire. If `seq(N)` returns no changes
while still below target, the drain **throws** (500) rather than ack a sync that
did not happen. On lock contention: record the seq in `scanpay_seq.ping`, answer
200, and let the incumbent drain it — a latency optimization over the keepalive,
not a correctness requirement.

**Tables** (`install.php`, latin1): `scanpay_seq` (`shopid` PK; `seq`, `ping`,
`mtime`); `scanpay_meta` (`orderid` PK; `shopid`, `subid`, `id`, `rev`, `nacts`,
`currency`, `authorized`/`captured`/`refunded`/`voided`); `scanpay_subs`
(`subid` PK; `rev`, `method` = payment-method *type*, not the pretty card label;
`method_exp`). `scanpay_subs` stores **no** retries, idempotency key, or `nxt`
lock — by design.

**Charge concurrency is intentionally lock-free — don't "fix" it.** No DB lock,
no `nxt` timestamp, no key rotation. The layers: local already-paid guards
(incl. an authoritative `scanpay_meta` SELECT); a stateless `Idempotency-Key` =
`orderid_rev_day`, enforced by Scanpay server-side at ≤1 charge per key per
24 h; WCS owns retry scheduling.

**Frontend TS** (built by esbuild): `public/assets/js/checkout.ts` (Blocks
registration; Apple Pay only offered where `ApplePaySession.canMakePayments()`
is true); `admin/assets/js/settings.ts` / `order.ts` / `subs.ts` (settings
sync/version UI, order meta box + capture, subscription meta box); shared
helpers in `admin/assets/js/util/compat.ts` and `types/meta.ts` (runtime
helpers, not just types).

## Lifecycle gotchas

- `install.php` runs on every activation and is idempotent. A fresh install
  stamps `wc_scanpay_version` so the loader skips `upgrade.php`. **"Fresh" =
  absent settings option, not absent version** — 1.x wrote settings but never a
  version, so gating on the version would skip the 1.x migration and leave
  auto-capture silently off.
- `upgrade.php` migrations are version-gated; the version is stamped **last** so
  an interrupted run retries from the start. On failure the loader
  **deliberately keeps** the `wc_scanpay_updating` transient: one retry per 5
  minutes instead of fataling `plugins_loaded` (which would take out wp-admin).
- **The API key is write-once**: custom `apikey` field, masked once set, never
  rendered back; an empty POST means *unchanged* (WC's default password
  handling would wipe the key); replacing a stored key is refused — reset
  button only. Saving settings validates the key with a live `seq(0)` when
  enabling or first setting it — a **UX check only**, nothing destructive hangs
  off it (a just-entered bad key is cleared so the field stays editable).
- **Only the reset button deletes data**
  (`admin/hooks/wp-ajax-wc-scanpay-reset.php`: drops the tables, clears the
  key, disables the gateways, re-runs `install.php`). Safe because sync replay
  rebuilds every meta row without re-firing `payment_complete()`.
- `uninstall.php` drops all tables, options, and the transient.
